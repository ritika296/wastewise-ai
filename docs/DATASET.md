# WasteWise AI — Dataset Documentation (Phase 2)

## This is synthetic data, not a real client's data

Generated by `ml/data/generate_dataset.py`, seed `42`, fully reproducible.
No real restaurant, chain, or sales figures are represented. It is built
to be *realistic enough to make forecasting genuinely hard* — not an
artificially easy toy problem.

## Shape

- **49,369 rows** after intentional duplicates (see below)
- 3 restaurant locations (Bengaluru, Pune, Hyderabad — different base
  demand multipliers: 1.15x / 0.90x / 1.00x)
- 30 menu items across 5 categories (Biryani & Rice, Main Course, Breads,
  Starters, Desserts, Beverages)
- 548 daily observations per item-location pair (2025-01-01 to 2026-07-02,
  ~18 months)

## What drives demand (the generative process)

| Factor | Effect | Real-world analogue |
|---|---|---|
| Item base popularity | Each of the 30 items has its own base daily demand (15–100 units) | Menu items are not interchangeable |
| Restaurant location | 0.90x–1.15x multiplier per location | Footfall/catchment differences |
| Day of week | Biryani/starters see a 30–40% weekend lift; beverages see a *slight weekday* lift (office lunch crowd) | Different items have different weekly rhythms — not a single blanket "weekend effect" |
| Seasonality | Temperature follows a sinusoidal annual curve (15–40°C); heat-sensitive items (cold beverages, ice cream) respond directly to it — verified: Cold Coffee averages 82 units/day in May vs. 45 in December | Real seasonal demand shift, not a label |
| Holidays | 1.35x multiplier on a defined Indian holiday calendar (17 dates across 2025–26) | Verified: 61.3 avg units on holidays vs. 48.6 non-holidays |
| Promotions | Each item gets 3–5 short promotional bursts (2–4 days) over the 18 months, with a 10/15/20% discount and a sub-linear demand lift | Verified: true (uncensored) demand +4.3% during promotions — real but modest, not an unrealistic spike |
| Special events | 6 city-wide demand-spike days (1.45x, all items, all locations) | Local festivals, cricket matches, etc. |
| Trend | Slow +8% organic growth across the full 18-month window | Avoids a perfectly stationary series, which would make forecasting artificially easy |
| Overdispersed noise | Gamma-Poisson mixture (not plain Poisson) around the true mean | Real demand is overdispersed, not Poisson-clean |

## The deliberate complication: censored demand

`units_sold` is **not** the same as true demand. Each day, a simulated
manager decides `inventory_available` (how much to prepare) based on a
*noisy* view of recent average demand — not the actual demand that will
occur. Then:

```
units_sold     = min(true_demand, inventory_available)
waste_units    = max(inventory_available - true_demand, 0)
stockout_flag  = true_demand > inventory_available
```

Calibrated to **17.2% of item-days stockout** and **waste ≈ 27% of
prepared inventory** — a real, worth-solving problem, not manufactured
chaos and not a negligible edge case.

**`true_demand` is included as a latent validation column and must NEVER
be used as a model feature or training target directly** — it would not
exist in a real deployment (if you knew true demand, you wouldn't need to
forecast it). Its purpose is narrow and specific: Phase 4 reports
forecast accuracy against *both* `units_sold` (what a naive approach would
train on) and `true_demand` (the honest target) so the PoC can show,
transparently, how much accuracy is lost to demand censoring on
historically-stocked-out days — a genuine, common real-world modeling
issue, not swept under the rug.

## Injected data-quality issues (for Phase 3 to catch)

| Issue | Volume | Purpose |
|---|---|---|
| Missing `temperature` values | 148 rows (0.3%) | Simulates sensor/API gaps |
| Duplicate rows | 49 rows (0.1%) | Simulates an export artefact |
| Negative `selling_price` | 6 rows | Simulates a data-entry error |

These are small and deliberate — large enough for the Data Quality module
(Phase 3/Module L) to have something real to catch and report, small
enough not to meaningfully distort the demand-generating process itself.

## What's simulated vs. what a real deployment would have

| This dataset | A real deployment |
|---|---|
| A fixed, hand-written holiday calendar | A maintained regional holiday API |
| A sinusoidal temperature curve | A real weather API feed |
| Random special-event days | Actual local event calendars |
| A single noisy "manager habit" model for preparation quantity | Real historical preparation-quantity records, if a client tracks them (many don't — this is itself a common PoC discovery finding) |

## Known limitations (stated upfront, not discovered later)

- 18 months captures only 1.5 annual cycles — a full 24+ months would let
  a model learn year-over-year seasonality more confidently; this is a
  PoC-scale trade-off, documented in the PoC Charter's Out-of-Scope.
- The promotion and special-event effects are deliberately modest — a
  model that only performs well by memorizing large synthetic spikes
  would be learning an artifact, not a transferable pattern.
- Weather here is a simulated seasonal curve, not real meteorological
  data — a Pilot would use a live weather feed.
